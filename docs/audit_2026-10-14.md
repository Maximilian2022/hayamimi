## 1. セキュリティ

### 【高】S1. HTTP/WS が認証なしで全NICに公開されている (README の記述と矛盾)
- `subtitle_server.py` L569: `SubtitleServer.__init__(host="0.0.0.0")`。`realtime_transcribe.py` L2452 は
  `SubtitleServer(port=args.serve, hub=hub)` と host を渡さないため **8833 は常に 0.0.0.0**。
- `launcher_gui.ps1` L1609 (Venv モード): `--ws-host 0.0.0.0` を常時指定。README は既定 `127.0.0.1`・
  「`/ingest` に認証なし、信頼できるネットワークのみ」と明記しているが、ランチャーがそれを上書きしている。
- WSLC モード: L1989/L2003 `-p 8833:8833 -p 8766:8766` (全IF公開)。`compose.yaml` L10-11 も同様で、
  nginx(TLS) を迂回して直接アクセス可能。
- 影響: 同一LAN上の誰でも ①`/events` で字幕(会話内容)を盗聴 ②`POST /config` `/reset` `/replacements`
  `/overlay-style` で設定改ざん ③`ws://…:8766/ingest` に接続しマイク入力を乗っ取り(preempt 仕様)。
- 備考: `--ws-host 0.0.0.0` は履歴 #41 で「IPv6 (`::1`) 対策」として追加されたが、0.0.0.0 は IPv4 のみで
  `::1` には効かない(実際の対策は `mic_page.html` の 127.0.0.1 優先)。**ほぼ不要な設定**の可能性が高い。
- 対策案: 既定を `127.0.0.1` にし、LAN公開は GUI のオプトイン(チェックボックス)で `0.0.0.0` +
  共有トークン併用。WSLC は `-p 127.0.0.1:8833:8833`。compose も同様。

### 【高】S2. ブラウザ経由の攻撃 (CSRF / 字幕盗聴 / CSWSH / DNS rebinding)
- `subtitle_server.py` L638, L785: `Access-Control-Allow-Origin: *` が `/events` と JSON 応答に付与。
  任意の Web サイトの JS が `localhost:8833/events` を購読して**字幕を読める**。
- POST 系 (L698-778) は `Content-Type` を検査せず `json.loads` する → `text/plain` の "simple request"
  でプリフライトなしに `/reset` `/config` `/overlay-style` を**他サイトから叩ける** (CSRF)。
  `Host` ヘッダ未検査のため DNS rebinding にも無防備。
- `ws_ingest.py` L150-157: `Origin` 未検査 → Cross-Site WebSocket Hijacking。任意サイトから
  `ws://127.0.0.1:8766/ingest` に接続して正規マイクを追い出し(L162-185)、`_forward_events`(L264) で字幕も受信可能。
- 対策案: ①`Origin`/`Host` の許可リスト(localhost/127.0.0.1/設定済みホスト) ②POST は
  `application/json` 必須 ③ACAO `*` を撤去(同一オリジン利用のみのため不要。OBS は ACAO 不要) ④任意で起動時ランダムトークン。

### 【高】S3. 管理者昇格スクリプトの TOCTOU (権限昇格)
- `launcher_gui.ps1` L1898-1901 / `setup.ps1` L499: 固定名 `%TEMP%\install_wsl3.ps1` を書き出し
  `Start-Process -Verb RunAs ... -ExecutionPolicy Bypass -File` で実行。UAC は `powershell.exe` の起動を
  承認するだけで内容は表示されない。書き込みから実行までの間に同一ユーザーの非昇格プロセスが差し替えれば管理者権限で実行される。
- 対策案: 管理者のみ書込可能なディレクトリ(`%ProgramData%\hayamimi\<guid>`)に ACL 付きで生成、
  実行直前に SHA256 を自己検証、または昇格側へ `-EncodedCommand` で直接渡す。

### 【中】S6. DoS 耐性 (WebSocket 自前実装)
- `ws_protocol.decode_frame` はペイロード長 (最大 64bit) の上限なし。`ws_ingest.py` L193-207 の `buf` は
  無制限成長 → 巨大 length を宣言して送り続けるだけで**メモリ枯渇**。
- ハンドシェイク完了前の接続でも L162-185 で既存クライアントを追い出す (未認証 DoS)。
- ハンドシェイク待ち/受信に**タイムアウトなし**(slowloris)、同時接続数上限なし。
- 対策案: 1フレーム最大長(例: 1MB)・`buf` 上限、`asyncio.wait_for` によるタイムアウト、
  追い出しは JSON ハンドシェイク成功後のみ、接続数上限。

## 2. メモリリーク / リソース枯渇

### 【高・確定バグ】M1. WS イベントミラーでスレッドリーク (`ws_ingest.py` L264-277)
`_forward_events` は `await loop.run_in_executor(None, q.get)` で待機する。タスクを `cancel()`
しても **executor スレッド内の `q.get()` は戻らない**。`unsubscribe(q)` 後は誰も `q` に put しないため
**永久にブロック**し、既定 ThreadPoolExecutor (`min(32, CPU数+4)`) のワーカーを1接続につき1本失う。
ブラウザのリロード/再接続/ネットワーク瞬断を繰り返すと枯渇し、**以降のイベント転送停止・
同 loop の他の `run_in_executor` もハング**する。
- 備考: memory.md #25 で SSE 側のゾンビキュー対策は済だが、WS ミラー側は未対応。
- 対策案: `q.get(timeout=1.0)` ループ + 停止フラグ、または unsubscribe 時に終端センチネルを put、
  もしくは `call_soon_threadsafe` で `asyncio.Queue` へブリッジ(スレッド不要)。

### 【中】M2. SSE `/events` の切断検知が遅れる (`subtitle_server.py` L640-649)
`q.get()` が無期限ブロックのため、切断は**次のイベント書き込み時にしか検知されない**。無音中に閉じたタブは
スレッド + 最大500件キューが残り続ける。`q.get(timeout=15)` で `: ping\n\n` を送る keepalive で解決
(プロキシ/OBS の無通信切断対策にもなる)。

### 【中】M3. 無制限キュー
- `TranslationWorker._q` (L1312)、`Refiner._task_queue` (L1469) は maxsize なし。翻訳を多言語選択 + CPU 高負荷時に滞留。
  Refiner のタスクは最大25秒分の音声コピー (L1872 `.copy()`、約1.6MB/件) を保持するためメモリが膨らむ。
- 対策案: 滞留閾値の警告イベント発行 + 古いタスクの破棄、または maxsize 設定。

### 【低】M4. 長時間稼働で単調増加するもの
- `SessionStats.latencies_ms` (L929/L1056)、`SpeakerLabeler._centroids/_counts/_confirmed/_open_log`
  (`speaker_id.py` L280-293)、`Refiner._recluster_entries` (L1454, 既知・コメントあり)。
  1件あたり小さいが数日連続稼働で積み上がる。`latencies_ms` は Welford 統計(平均/最大のみ)に置換可能。
  `_centroids` は話者数に比例して `match_embedding` が O(N) になる。

### 【低】M5. その他リソース
- `TranslatorPool.add_target` (L1249-1262) は**ロックを保持したままモデルロード**。ロード中
  `items()`/`targets` が全てブロックされ、翻訳ワーカーも停止 (数秒)。ロード後にロックを取り直す方式が望ましい。
- `partial` を非TTY (`logs/python.log` へリダイレクト) 時も 0.5秒ごとに1行出力 (L917) → ログが無制限に肥大。
  非TTY時は partial を抑止、またはログローテーション。
- `_get_storage_dir()` が呼び出しごとに書込テストを実行 (キャッシュ推奨)。

### 良い点
`EventHub` のバウンデッドキュー、`audio_q` の上限、`RoutedASR.close()`/`Refiner.close()` による
スレッド・モデル解放、M2M 共有キャッシュ、DOM 件数上限は適切に実装済み。

## 4. その他の気づき

1. **Python バージョン不整合**: requirements/venv/CI は 3.11、`Dockerfile` は `python:3.14-slim`。
   `sherpa-onnx==1.13.6` / `onnxruntime==1.29.0` 等の cp314 wheel の有無が未確認で、**コンテナビルドが失敗するリスク**
   (今回は検証していない)。3.11 か 3.12 にそろえるのが安全。
2. **ルーティング**: `do_GET` は `self.path` 完全一致のため `/mic?x=1` `/events?x=1` が
   オーバーレイ HTML にフォールバックし、未知パスも 404 にならない。`urllib.parse.urlparse` 利用を推奨。
   `int(Content-Length)` は不正値で例外 → 400 に。L646 の `except (…, Exception)` は広すぎる。
3. **CI**: テストのみ。`pip-audit`/Dependabot、PSScriptAnalyzer、Docker ビルド検証がない。
   `actions/*` はタグ固定(SHA 固定が望ましい)。CI は `requirements.txt` ではなく個別 pip install で実環境と乖離。
4. **巨大ファイル**: `launcher_gui.ps1`(約3,080行/150KB)、`realtime_transcribe.py`(約2,700行)、
   `asr_engine.py`(約1,940行)。分割して保守性・テスト容易性を向上できる。
5. **scripts/ の整理**: 実行系と評価・データ作成系 (`eval_*` 13本、`make_*` 9本、`*_candidates.py` 等) が混在。
   `tools/` 等へ分離すると配布物が見通しやすくなる。削除はユーザー判断(今回は未削除)。
6. `git pull origin main` はローカル変更ありの環境で失敗しうる(失敗時 ZIP にフォールバックはあり)。
7. 証明書 365日失効・更新通知なし (S5 再掲)。
